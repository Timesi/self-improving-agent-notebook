## Lecture theme

The core problem this lecture solves: **an agent's context window is finite, but the information tasks need (long conversations, long documents, long-term personalization) is infinite. What then?**

Placement: after lecture 10 SWE agents (the agent works repeatedly in a long codebase / long issue, strongly exposing the context bottleneck) and before lecture 14 evaluation, dedicated to "memory". The first three papers split "memory" into three complementary layers:

1. **MemGPT — hierarchical organization of memory (software layer / control layer)**: treat the context window as scarce memory, imitate OS virtual-memory paging, use function calls so the LLM itself "pages" — put currently most relevant information in main context, evict old information to external storage, retrieve it back when needed.
2. **Cartridges — learnable compression of memory (representation layer)**: rather than decide "which text goes into context", distill the whole corpus into an offline-trained KV cache (learnable parameters). This turns "memory" from discrete tokens into a continuous vector representation, the other extreme of MemGPT's "token moving" idea.
3. **CacheBlend — cross-request reuse of memory (system layer / engineering layer)**: when several requests share the same batch of text chunks, how to reuse their precomputed KV cache without losing quality. It handles "cross-attention loss at reuse time", the engineering infrastructure that makes the above memory mechanisms actually fast.

A through-line intuition: **memory is not "stuff more tokens", but "use smarter storage/representation/reuse so finite context exerts infinite ability"**. The lecture goes from "software control" to "learnable representation" to "system reuse", a three-step staircase from abstract to engineering.

## Close reading

### Paper 1: MemGPT: Towards LLMs as Operating Systems (arxiv:2310.08560, memgpt.pdf)

- **Core idea**: analogize an LLM's fixed context window to an OS's "physical memory", add a "disk" (external storage) outside it, then use the LLM's function-calling ability to implement "virtual-memory paging" — the LLM itself decides which information to page in (main context) and which to page out (external context), thus providing the illusion of "infinite context" on a finite window. The system is named MemGPT (MemoryGPT), uses an OS-style hierarchical memory architecture, and is evaluated on long-document analysis and multi-session dialogue.

- **Key formulas / algorithms**:
  - **Two-layer memory hierarchy**: *main context* (analogy RAM, i.e. the LLM's prompt tokens, visible at inference) and *external context* (analogy disk, outside context, must be explicitly paged into main context to be used at inference).
  - **Main context in three segments** (fixed order, concatenated):
    - *system instructions*: read-only, static, containing control-flow notes, the use of each memory layer, function-usage notes.
    - *working context*: fixed-length, read-write unstructured text, writable only via functions; in dialogue, stores key user facts, preferences, persona.
    - *FIFO queue*: rolling message history (user/assistant messages, system messages, function-call args and returns); the queue's first index stores a "recursive summary" (recursive summary of already-evicted messages).
  - **Queue Manager**: a new message arrives → append to the FIFO queue → concatenate prompt tokens → trigger LLM inference → write the input message and generated output into *recall storage* (message database).
  - **Eviction policy**: when prompt tokens exceed *warning token count* (default about 70% of context), insert a "memory pressure" system message into the queue, prompting the LLM to use functions to save important information into working context or *archival storage*; when exceeding *flush token count* (100%), flush the queue — evict about 50% of context's messages, generate a new recursive summary from the existing recursive summary + evicted messages. Evicted messages are no longer visible in context, but live permanently in recall storage, retrievable anytime via functions.
  - **Function executor**: parse the LLM's completion tokens into function calls, validate args then execute, feed results (including runtime errors) back to the LLM. Self-directed read/write: function schemas and natural-language descriptions are written into system instructions; the LLM autonomously decides when to append/replace its own memory. Typical functions: `working_context.append`, `working_context.replace`, `recall_storage.search`, `archival_storage.search`/`insert`. Retrieval has pagination, preventing results from overflowing the window.
  - **Control flow / function chaining**: events (user messages, system messages, user interactions such as "login/upload done", timed events) trigger inference; the LLM can include a special `request_heartbeat=true` parameter in output, requesting another inference immediately, thus chaining multi-step retrieval; without that flag (yield) it pauses, waiting for the next external event.
  - Archival storage uses PostgreSQL + pgvector (HNSW index) for vector retrieval (cosine); a "retriever" naturally emerges from external-storage search.

- **Key experimental results**:
  - **Deep Memory Retrieval (DMR, cross-session consistency)**: narrow-answer questions about previous-session content. MemGPT substantially beats a fixed-context baseline: GPT-3.5 Turbo 38.7%→66.9% (ROUGE-L 0.394→0.629); GPT-4 32.1%→92.5% (0.296→0.814); GPT-4 Turbo 35.3%→93.4% (0.359→0.827). The baseline can see a "lossy summary" of the past 5 dialogues; MemGPT holds the full history but can only page-retrieve.
  - **Conversation Opener (engagement)**: how personalized the opening is. MemGPT can approach or even beat human-written openings (SIM-H: Human 1.000, GPT-3.5 0.817, GPT-4 0.773, GPT-4 Turbo 0.767). Storing information in working context is key.
  - **Document QA (NaturalQuestions-Open)**: a fixed-context baseline's accuracy is "capped" by retriever performance (only documents stuffed into context are visible), and falls as truncation worsens; MemGPT is unaffected by retrieved-document count, can repeatedly query archival storage and paginate, so effective context is no longer window-limited.
  - **Nested KV retrieval (multi-hop)**: 140 UUID pairs (about 8k tokens, i.e. GPT-4's window size), nesting depth 0–4. GPT-3.5 drops to 0% at nesting 1; GPT-4 / GPT-4 Turbo drop to 0% at nesting 3; MemGPT+GPT-4 is insensitive to nesting depth (repeatedly uses functions to look up key-value pairs in main context).
  - Motivation numbers: context is short (Table 1: Llama 2k, Llama 2 4k, GPT-4 at release 8k, Claude 2 100k, GPT-4 Turbo 128k, Yi-34B-200k 200k), and long-context models "remember well only at the start and end, lose the middle" (lost in the middle, citing Liu et al. 2023). Release data: expanded MSC, nested KV, 20M Wikipedia-article embeddings.

- **Relation to the lecture theme**: this paper gives the first answer to "memory" — **hierarchical memory managed by the agent itself**. It defines the standard vocabulary of agent memory (main/external context, working memory, recall/archival storage, eviction, recursive summary, memory-pressure warning), the lecture's conceptual foundation. It connects naturally to earlier tool calling (L04) and the ReAct loop (L05): function calls extend from "operating the outside world" to "operating one's own memory".

### Paper 2: Cartridges: Lightweight and general-purpose long context representations via self-study (arxiv:2506.06266, cartridges.pdf)

- **Core idea**: many applications repeatedly stuff the same large corpus (codebase, 10-K, medical record, chat log) into context (ICL). ICL's cost is that the KV cache grows linearly with input, so serving cost is extremely high. Cartridges propose **offline training a "small KV cache" for each corpus** (trainable parameters, essentially a simplified prefix-tuning); at inference load this trained KV cache (called a *Cartridge*) into the LLM, then concatenate the user query and decode. Training cost can be amortized over "repeated queries of the same corpus". Key finding: training on the corpus with next-token prediction (NTP) directly does not work (only recites, does not generalize); they propose a **Self-study** recipe: let the model itself generate synthetic dialogues about the corpus, then train with a **context-distillation objective**, thus replicating ICL's function.

- **Key formulas / algorithms**:
  - **Cartridge parameterization**: `Z = {zk, zv} ∈ R^{p×d}` (p trainable key/value vectors per layer), memory occupancy equivalent to "a p-token KV cache". Method: replace the n_C K/V pairs corresponding to corpus C in ICL's KV cache with Z, freeze all other parameters, backprop the loss only onto Z's key/value vectors.
  - **Initialization (key trick)**: initialize Z as "the KV cache of the first p tokens of corpus C". Ablation (LongHealth accuracy): random vectors 29.9%, random-token K/V 51.3%, first p tokens of the corpus 55.3%. Random initialization is unstable and performs poorly (echoing the original prefix-tuning conclusion).
  - **Self-study synthetic data (Algorithm 1)**: ① chunk the corpus (512–4096 tokens, supporting ultra-long corpora); ② take a seed prompt; ③ let the same LLM play roles A and B, alternately sample k rounds of dialogue (A's history contains the seed prompt + corpus sub-chunk in the system prompt; B's history has no seed prompt, but roles are swapped), concatenate into a training sequence `x = a1 ⊕ b1 ⊕ … ⊕ ak ⊕ bk`. Main experiments use single-round dialogue k=1.
  - **Seed prompts**: 5 general types (structuring, summarization, question, use cases, creative), the same set shared by all corpora, containing no corpus-specific information. Randomly sampling 5 kinds beats a single seed: LongHealth +4.8 accuracy (43.6→48.4), MTOB +7.9 chrF (24.1→32.0).
  - **Context-distillation objective**:
    `argmin_Z Σ_{(x,c̃)∈D} Σ_{i=1}^{|x|} D_KL( F(·|c̃ ⊕ x[:i]) || F_Z(·|x[:i]) )`
    Teacher = model distribution with corpus sub-chunk c̃ in context, student = the same model's distribution with a Cartridge. Beats NTP at the same data volume: MTOB +8.6 chrF (24.9→33.5), LongHealth +3.7 accuracy.
  - Ablation: **KV-cache parameterization beats LoRA** — on MTOB, same-memory prefix-tuning is 4.5 chrF higher; more critically, damage to unrelated queries (MMLU): LoRA falls from 54.7 to 45.3 as size grows, prefix-tuning only from 54.7 to 54.3. Freezing the attention sink (first token's K/V) improves training stability. Training cost: an ICL-quality Cartridge for LLaMA-8B is about 30 minutes / one 8×H100 node.

- **Key experimental results**:
  - **Core numbers**: across benchmarks on average, Cartridges match ICL quality, with **38.6×** less memory and **26.4×** higher peak throughput. LongHealth saves up to 10×, QASPER up to 100× memory; compression-class baselines (truncation, GPT-4o summary, DuoAttention) collapse in quality above 2× compression, while a Cartridge is trained compression.
  - **NTP's failure**: with 107× less memory it recites the corpus perfectly, but only performs well on "recitation-class" queries; other query types (reasoning/structure/creative) do not generalize.
  - **Context-length extrapolation (MTOB)**: LLaMA-8B (128k window) with Self-study chunking handles a 484k-token Kalamang textbook, **11.0 chrF** above ICL on the first 130k tokens, and matches ICL on a hand-picked 60k subset — corpora that do not fit the window can still be used.
  - **Composability**: two independently trained Cartridges (AMD 10-K, Pepsi 10-K) concatenated directly can answer cross-document questions, no joint training; substantially beats "only one Cartridge" and "truncated ICL" (the latter needs 39.8 GB context). Datasets: LongHealth, MTOB, QASPER, GENCONVO (from FinanceBench).

- **Relation to the lecture theme**: this paper gives the second answer to "memory" — **make memory a learnable continuous representation**. MemGPT moves tokens at the "control layer"; Cartridges compress a whole corpus into a KV cache at the "representation layer". It also shows ICL's essence: ICL quality can actually be "distilled" into parameters, swapping "expensive runtime context" for "cheap offline representation". This has direct implications for "an agent's long-term memory" (e.g. remembering a user's entire chat history) and "a coding agent's full-repo context", and is a preview of combining reasoning/math with compression in later lectures 12/13.

- **Demo-ready code points**:
  - With a small transformer (causal self-attention from scratch in torch, or load a small open-source model), freeze weights, train p trainable K/V vectors, on a toy corpus contrast generalization of the NTP objective vs the context-distillation objective.
  - Hand-calculate/visualize initialization importance: training curves under random / random-token / first p-tokens-of-corpus initialization.
  - On a toy corpus demo "recitation vs generalization": an NTP-trained Cartridge can continue but cannot answer questions; after Self-study data + KL distillation it can answer.
  - Demo Cartridge composition: concatenate two independently trained Cartridges then answer a cross-document question that needs both.

### Paper 3: CacheBlend: Fast LLM Serving for RAG with Cached Knowledge Fusion (arxiv:2405.16444, cacheblend.pdf)

- **Core idea**: a RAG input is concatenated from several text chunks; prefill (compute KV cache for the whole input) is slow and determines time-to-first-token (TTFT). Existing two classes of KV-reuse schemes each have a defect: *prefix caching* (vLLM/SGLang/RAGCache) only reuses the prefix chunk's KV, other chunks still prefill, almost useless in multi-chunk scenes; *full KV reuse* (PromptCache) reuses all chunks but ignores **cross-attention** between chunks (and between chunks and preceding text), so quality collapses. CacheBlend proposes **selective KV recompute**: per layer recompute only a small fraction of tokens' KV (the rest reused), thus getting both full-KV-reuse speed and full-KV-recompute quality; the tiny extra recompute latency can also pipeline-overlap with "loading KV cache from slow storage", so the KV cache can live on slower cheaper devices without adding latency.

- **Key formulas / algorithms**:
  - **Motivation numbers**: a 4000-token input on one A40 takes 3s to prefill (Llama-34B) / 6s (Llama-70B).
  - **Notation**: `KV_full` (fully recomputed cache), `KV_pre` (precomputed cache), `KV_new` (cache after CacheBlend update); each layer i produces a forward attention matrix `A_i`. Define **KV deviation** `Δkv(KV_i, KV_full_i)[j] = |KV_i[j] − KV_full_i[j]|` (how much a token's K/V at a layer deviate from full recompute), and **attention deviation** `Δattn(A_i, A_full_i)` (L-2 norm difference of forward attention matrices). Goal: quickly update KV_pre to KV_new so each layer's `Δattn(A_new_i, A_full_i)` is minimized.
  - **Selective-recompute workflow (per layer)**: mask each layer's input to keep only selected tokens → compute Q/K/V only for selected tokens → fill unselected tokens' K/V back from the precomputed cache (so the attention matrix still includes attention of selected tokens to all tokens) → run the same attention module to get the next layer's input. Compute cost ∝ selected-token count: recomputing r% of tokens costs r% of full prefill.
  - **Which tokens to recompute (HKVD)**:
    - Insight 1: recomputing tokens with higher KV deviation contributes more to lowering attention deviation → each layer picks about 10–20% of tokens with highest KV deviation (High-KV-Deviation, HKVD).
    - Insight 2: a token's KV deviation is highly correlated across adjacent layers (high Spearman rank correlation, because transformer adjacent-layer input embeddings change slowly) → no need to fully compute deviation every layer; use **progressive screening**: layer 1 fully recomputes and picks r1% (slightly above target r) tokens, the next layer picks r2% (slightly below r1%) only among those r1% to continue recomputing, converging layer by layer.
  - **Why it is enough**: attention sparsity — about 10–15% of tokens have far higher KV deviation than others; only tokens with high attention to other chunks (high cross-attention) need recompute.
  - **RoPE position recovery**: precomputed chunks' K vectors only need to be multiplied by a rotation matrix (`[cos mθ, −sin mθ; sin mθ, cos mθ]`), because under RoPE attention scores depend only on relative position (appendix gives a proof). This step's cost is negligible.
  - **Pipeline and loading control (Loading Controller)**: layer i's recompute can start after layer i−1's KV is loaded → hide recompute latency with KV-load latency. Two latency estimators (`T_recompute(r%, LLM, L) = r% × Prefill(LLM, L)`, `T_load(LLM, L, device) = PerTokenKVSize × L / Throughput(device)`), pick r so they are equal, then take max with quality floor r* = 15%; or fix 15% recompute rate, pick the "cheapest device with T_recompute ≥ T_load". Example: Llama-7B recompute 15% is 3ms per layer, loading one layer of KV from NVME SSD needs 16ms → latency is fully hidden.
  - **KV cache store**: split input by text chunk (application-dependent; the paper follows PromptCache's strategy), hash chunk text to look up cache, LRU eviction; the hash table lives on CPU (1 million chunks only 16MB).

- **Key experimental results**:
  - **TTFT down 2.2–3.3×, throughput up 2.8–5×** (vs full KV recompute), quality loss ≤0.01–0.03 (F1/Rouge-L). Vs prefix caching also TTFT 2.2–3.3× down, throughput up.
  - Vs full KV reuse: almost the same TTFT, but QA F1 0.1–0.2 higher, summarization Rouge-L 0.03–0.25 higher (full KV reuse quality is often more than 2× worse).
  - At 5%–18% recompute rate, quality loss vs full KV recompute ≤0.002, convertible to TTFT down 4.1–6.6×.
  - Quality rises with chunk count (F1 from about 0.15 to 0.35 range); the gap between full KV reuse and full prefill widens as chunks increase → showing cross-attention is common in real multi-chunk scenes. Outside RAG, CacheBlend also beats LangChain MapReduce (TTFT 2–5× lower, F1 higher) and MapRerank (quality much higher).
  - Models: Mistral-7B, Yi-34B, Llama-70B (the latter two 8-bit quantized); datasets: 2WikiMQA, Musique (QA, F1), SAMSum, MultiNews (summarization, Rouge-L); chunks 512 tokens, take top-6 chunks (L2 distance).

- **Relation to the lecture theme**: this paper gives the third answer to "memory" — **make memory reuse fast at the engineering/system layer**. The previous two care about "what is stored in memory, how to organize/compress"; this one cares about "when the same piece of memory is used repeatedly, how to save prefill". It is the serving infrastructure that lets mechanisms like MemGPT/Cartridges actually land: reused-context KV cache + recovering cross-attention across chunks + slow cheap storage. In the course it connects "memory" to "cost/throughput", matching lecture 14's engineering orientation (agents need to serve at scale).

- **Demo-ready code points**:
  - Hand-calculate a 2-chunk attention matrix: construct a two-chunk question like "Messi/Ronaldo goals", contrast forward-attention matrix differences under full recompute, full KV reuse (no cross-attention), CacheBlend (recompute only HKVD tokens) (numpy).
  - Implement HKVD selection and progressive screening from scratch: given two adjacent layers' KV-deviation matrices, compute top-r% tokens and Spearman rank correlation, verify "high inter-layer correlation".
  - Reproduce attention sparsity: on toy attention plot the CDF of KV deviation, observe that 10–15% of tokens account for most deviation.
  - With a latency model demo the pipeline: simulate `T_recompute(r)` and `T_load(device)`, let students pick r and storage device (copy the paper's Loading Controller decision).

## Teaching thread (how a Stanford instructor might teach this)

Suggested lecture order and intuition analogies:

1. **A failure case sets motivation**: show a "goldfish memory" assistant — last session remembered the user's birthday and preferences, this session forgot them all; or a 10-K far exceeds what context can hold. Raise the problem: an agent needs to run long-term, the context window is a hard constraint, and long-context models "lose the middle" (lost in the middle, evidence cited in MemGPT's introduction). **Here the first sentence: what an agent lacks is not parameters, but memory.**
2. **OS analogy: hierarchical memory**: how does an OS use "physical memory + disk + paging" to pretend it has infinite memory? Analogize the LLM's context to memory, external storage to disk, function calls to paging instructions (page in / page out). That is MemGPT's whole skeleton. Use figure 3's memory-hierarchy figure to make main context's three segments (system/working/FIFO) and external context's two stores (recall/archival) clear.
3. **Control mechanism: who decides what to move**: MemGPT's essence is "self-directed" — the LLM itself decides when to append/replace/evict/retrieve. Make the closed loop memory-pressure warning (70%) → flush (100%) → recursive summary, and request_heartbeat function chaining, clear. Where readers most easily stall: **why recursive summary rather than delete directly? Why should eviction involve the LLM rather than hard LRU?** (Answer: memory hides semantic importance; LLM judgment is better than a fixed policy; but it can also be pointed out this is a cost — every time burns tokens.)
4. **From "moving tokens" to "learning a representation"**: point out MemGPT's limit — memory operations all go through text, burn tokens, constrained by the window. Turn to Cartridges: can we not move text, but compress the whole corpus into a trainable KV cache? Here make prefix-tuning's essence clear: add p "virtual tokens" in front of the input, but this time train one per corpus, training cost amortized across queries.
5. **Self-study's three design decisions**: why NTP does not work (recitation does not generalize) → synthetic dialogue data (two roles Q&A each other, 5 seed prompts) → context-distillation objective (teacher = corpus in context, student = with Cartridge). Each decision with an ablation figure (Figure 3/6). Here can hand-calculate one page of the KL distillation formula, so readers see "align distributions" rather than "recite text". Where readers stall: **why does distillation rather than NTP generalize?** (Because distillation teaches "answering behavior when facing the corpus"; NTP only teaches "what the corpus itself looks like".)
6. **Back to the system layer: reusing KV is reusing memory**: if a Cartridge is a piece of "trained memory", then chunks that repeatedly appear in RAG actually share the same "memory" (precomputed KV cache). Raise CacheBlend's problem: full reuse drops cross-attention. Use a Messi/Ronaldo contrast question as an example, so readers see with their own eyes "compute KV on two chunks separately then concatenate, the model answers wrong".
7. **Hand-calculate / visualize understanding**: on one page draw three schemes' attention matrices (full recompute / full KV reuse / CacheBlend selective recompute), intuitively seeing whether the yellow cross-attention block is present. Then HKVD selection (Insight 1, Insight 2, progressive screening) and "attention sparsity → 10–15% of tokens are enough".
8. **System engineering**: Loading Controller pipeline (load the next layer while recomputing one layer), making slow SSDs feasible. Finally fold the three papers into one sentence: **MemGPT decides where memory lives, Cartridges decide what memory looks like, CacheBlend makes memory reuse cost nothing** — and preview that they will appear in later lectures (e.g. 12/13 reasoning, 14 evaluation).
