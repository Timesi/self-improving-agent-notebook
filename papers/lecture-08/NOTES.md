## 课程主题

这一讲回答一个核心问题：当"单次生成一个答案"不够用时，Agent 如何借助**搜索**来显著提升复杂任务的表现。搜索的对象可以很不一样：AlphaCode 在**程序空间**里搜索（为一道题生成上百万个候选程序，再挑出最值得提交的），Search-o1 在**知识空间**里搜索（在长推理过程中按需检索外部知识补上知识缺口）。两者共享同一个骨架：**生成 → 验证/过滤 → 挑选/继续**。

这一讲的位置很关键。前面 L6 讲 test-time compute scaling（推理时更多计算换更好结果）、L7 讲开放进化（用搜索+验证循环让智能体自我改进），本讲把"搜索"推向两个具体、可动手复现的系统级案例，并为后面的 deep research agents 工作流（第 4 节）提供原语：**reasoning-actor（决定何时搜索）+ retrieval-critic（精炼检索结果）**。它是"模型自省推理"到"模型主动调用外部世界"的桥梁，也衔接 L9 的后训练演进。

## 论文精读

### 论文 1：Competition-Level Code Generation with AlphaCode（arXiv:2203.07814，alphacode.pdf）

- **核心思想**：程序合成是一个在**巨大且结构化**的程序空间里搜索、且奖励信号极其稀疏的问题——单个字符改动就能改变程序行为，同一道题的合法解可以长得完全不同，而"这个程序是否接近正确"又很难判断。AlphaCode 的应对是把问题建模成序列到序列翻译（自然语言题面 → 程序），用一个大型 encoder-decoder transformer，在推理时做**大规模采样 + 基于行为的过滤 + 聚类**，把每道题最终压缩到最多 10 个提交。这是第一个在编程竞赛中达到"中位选手水平"的 AI 系统。

- **关键公式/算法**：
  - **数据**：先在 715.1 GB 的精选 GitHub 代码上预训练；再在自建 CodeContests 数据集上微调（train 13328 / valid 117 / test 165 题，严格按时间切分防泄漏）。用**测试变异生成**额外测试（翻转 bit、随机增删整数、改字符串），把数据集的 false positive 率从 62% 压到 4%。
  - **模型**：encoder-decoder transformer，规模 300M 到 41B 参数；非对称结构（encoder 1536 tokens / decoder 768 tokens，题面平均是解答的两倍长）；multi-query attention 主要为了**采样更快**。
  - **微调**：GOLD 目标 + tempering + value conditioning/prediction + 随机 tags/ratings 条件化。
  - **采样**：每道题最多采样 10^6 个候选；一半 Python 一半 C++；随机化 prompt 里的标签（从最流行的 50 个里随机选）和难度评分（800-3500 均匀采样）以增大多样性；采样温度 0.25。采样可并行，是性能提升的关键杠杆。
  - **过滤（验证器）**：把每个候选程序在题面给的**样例测试**上执行，删掉输出不匹配者。这能移除约 99% 的样本（通过样例测试的样本 <1%）；约有 10% 的题一个通过样例测试的样本都找不到。过滤是"在无监督验证信号下压缩候选"。
  - **聚类（多样性管理）**：过滤后仍可能剩几千个候选，但只有 10 次提交机会。AlphaCode 训练了另一个"**测试输入生成模型**"，从题面生成新的测试输入，把所有剩余程序跑一遍，把输出相同的程序按**行为签名**聚类。正确解行为相似，会聚成**最大的簇**，因此按簇大小从大到小取前 10 个簇、每簇挑一个提交，能最大化覆盖不同正确解。
  - **指标**：`10@k`（允许从 k 个样本里挑 n=10 个提交的通过率）和 `pass@k`（k 个样本全提交，即 k@k，是理论上界）；用 bootstrap 估计期望以降低方差。`10@k` 与 `pass@k` 之间的差距正衡量了**挑选算法的质量**。

- **关键实验结论**：
  - Codeforces 10 场近期竞赛（每场 >5000 参与者）平均排名**前 54.3%**，估算 Codeforces rating 1238（超过最近 6 个月参赛用户中的 72%）；平均每个解出的题只用了 2.4 次提交。
  - CodeContests：41B + clustering 在 validation 上 `10@1M = 34.2%`，test 上 `10@100k = 29.6%`（无泄漏的完全未见题）。
  - **求解率随样本数近似 log-linear 增长**，且更大的模型斜率更高（图 6）；提高采样预算的收益是指数级成本换对数级提升。
  - 消融：仅过滤而不用聚类时求解率上不去（图 8 三条曲线对比），**过滤+聚类是让"更多采样"转化为"更高求解率"的必备环节**；每个增强（MLM、tempering、tags/ratings、value、GOLD、clustering）逐个加上，把 `10@100k` 从 15.2% 抬到 24.1%。
  - 模型不靠背题：最长公共子串分析与人类选手同量级，主要是输入解析样板代码，不是核心逻辑。

- **与课程主题的关系**：AlphaCode 是"**程序合成即搜索**"的教科书案例，也是本讲第一块基石。它把 L6 的 test-time compute scaling 落到一个具体系统：推理阶段用掉大量采样计算来**探索**候选空间，用样例测试做**廉价验证器**，用行为聚类做**去冗余的挑选**。三个环节缺一不可，这正是后面所有"生成 → 验证 → 挑选"Agent 循环的雏形。

- **可演示的代码点**：
  - 从零实现"采样 → 过滤 → 聚类"管线（用 `llm_client` 的 脚本化 或真实模型生成候选，python 执行样例测试过滤，随机输入跑出行为签名再聚类）。
  - 画 `10@k` 与 `pass@k` 随采样数的两条 log-linear 曲线，直观看到"过滤+聚类"把 10@k 拉向 pass@k。
  - 在合成小程序空间里演示行为聚类：正确解聚成一个大簇，错误解散落成小簇。

### 论文 2：AlphaCode 2 Technical Report（2023-12-06，alphacode2-report.txt / alphacode2-report.pdf）

- **核心思想**：AlphaCode 2 是 AlphaCode 的升级系统，把基座换成 Gemini Pro，保留并强化"**大规模采样 + 过滤 + 聚类**"三件套，并新增一个**重排序（scoring model）**环节，在 Codeforces 上解出 43% 的题，达到估算的**第 85 百分位**（AlphaCode 只有 46%）。更惊人的是样本效率：AlphaCode 2 用约 100 个样本就追平 AlphaCode 用 100 万个样本的表现（**>10000× 更省采样**）。

- **关键公式/算法**：
  - **policy 模型族**：以 Gemini Pro 为起点，用 GOLD 做两轮微调（先 CodeContests v2，再一个更高质量的数据集），通过变动超参数得到一族策略模型，用**一族模型**而非单个模型来最大化输出多样性。
  - **采样**：每道题最多 10^6 个样本，随机采样温度，随机化 prompt 元数据（难度评分、分类标签）；预算在模型族内均分；**只用 C++**（实验发现 C++ 样本质量更高）。
  - **过滤**：用样例测试执行过滤，去掉输出不匹配者和编译失败者（<5%），平均移除约 **95%** 的样本。
  - **聚类**：过滤后平均剩 5 万个候选；沿用 AlphaCode 的思路——单独训练测试输入生成模型，用新输入跑出行为签名聚类，按簇大小排序，只保留 **10 个最大的簇**，避免冗余提交。
  - **Scoring model（新环节）**：微调第二个 Gemini Pro 专门给程序打 0-1 的"预估正确性"分数；在每个簇内用打分选出最好的一个候选，凑成最终 10 个提交。这是从"按簇挑一个"升级为"按簇内预估正确性挑一个"。

- **关键实验结论**：
  - Codeforces 12 场近期竞赛（>8000 参与者，div2 或 1+2）、共 77 题：解出 **43%**，是 AlphaCode（25%）的约 1.7 倍。
  - 估算排名**第 85 百分位**（介于 Codeforces 的 Expert 与 Candidate Master 之间）；表现最好的两场超过 99.5% 的参赛者。
  - **样本效率**：约 100 个样本即达到 AlphaCode 用 100 万个样本的性能，**>10000×** 更省采样；求解率仍随样本数近似 log-linear 增长（图 3）。
  - 与人类协作（额外提供过滤规则）时得分超过第 90 百分位。

- **与课程主题的关系**：AlphaCode 2 展示了"搜索系统"的**演进方向**：在同样的三件套上叠加一个**学习出来的重排序器**，并把基座模型换强。两条教训：(1) 过滤/聚类/重排序是"把海量生成变成有限次高质量提交"的工程核心；(2) **基座模型质量与所需搜索量存在强烈权衡**——模型每好一点，需要的采样量就指数级下降，这解释了为什么持续提升模型（后训练、RL）与做好搜索同样重要。

- **可演示的代码点**：
  - 给 AlphaCode 式管线加一个简单的 reranker：用"候选在额外随机输入上的表现/输出一致性"或一个微调打分器给候选排序，对比随机提交、纯过滤、过滤+聚类、过滤+聚类+打分的 `10@k`。
  - 模拟"模型质量 ↑ → 所需采样量 ↓"：用不同质量的模拟生成器画 log-linear 曲线族，观察高质量模型向左平移（更少样本达到相同求解率）。
  - 对比"10 个最大簇每簇选一个"与"选簇内打分最高"两种提交策略的差异。

### 论文 3：Search-o1: Agentic Search-Enhanced Large Reasoning Models（arXiv:2501.05366，search-o1.pdf）

- **核心思想**：o1 类**长推理模型**（LRM，如 OpenAI o1、QwQ、DeepSeek-R1）靠大规模 RL 练出逐步长链推理，但在知识不足时经常出错——统计显示推理过程里高频出现不确定词（"perhaps"平均每个输出出现 30.4 次）。标准 RAG 只按**原始问题**检索一次，对多步推理中各步不同的知识缺口几乎没用。Search-o1 把**agentic RAG**（推理过程中按需、多次、自触发检索）嵌进推理链，并加一个 **Reason-in-Documents** 模块先把检索文档**精炼**再注入，避免冗长冗余文档打断推理连贯性。

- **关键公式/算法**：
  - **Reasoning-actor（何时搜）**：推理模型在生成推理链 $R$ 时，遇到不确定知识就自行输出一个搜索查询，用特殊符号包裹：`<|begin_search_query|>...<|end_search_query|>`。检测到结束符即**暂停推理**，抽取查询 $q^{(i)}_{search}$，调用检索函数 $D^{(i)}=\mathrm{Search}(q^{(i)}_{search})$（实现用 Bing Web Search API，top-k=10）。
  - **Retrieval-critic（怎么用）**：Reason-in-Documents 模块独立于主推理链运行：给定当前推理链 $R_{<i}$、搜索查询 $q^{(i)}_{search}$、检索文档 $D^{(i)}$，先生成中间分析 $r^{(i)}_{docs}$（理解文档），再产出精炼知识 $r^{(i)}_{final}$，以 `<|begin_search_result|>...<|end_search_result|>` 的形式插回主链，推理继续。
  - **推理循环**：生成推理步 → 遇到查询就检索+精炼+注入 → 继续生成 → 直到 EOS。整个过程在**一条推理链内可触发多轮检索**，各步知识需求不同也不怕。
  - **批量推理**：对一批问题并行维护"未完成序列集 S / 已完成集 F"，所有序列并行生成到 EOS 或查询结束符，然后批量检索、批量精炼、批量插回，提升吞吐。
  - **生成设置**：max 32768 tokens、温度 0.7、top_p 0.8、top_k 20、重复惩罚 1.05，主干是开源的 QwQ-32B-Preview；检索不到答案时回退到直接推理结果。
  - 数学形式：把推理建模为 $P(R,a|I,q,D)=\prod_t P(R_t|R_{<t},I,q,D_{\le t})\cdot\prod_t P(a_t|a_{<t},R,I,q)$，检索发生在 token 级别被插入推理链。

- **关键实验结论**：
  - GPQA diamond（198 题，博士级科学问答）：Search-o1 总体 **63.6%**，超过直接推理 QwQ（58.1%）和 agentic RAG 基线 RAgent（61.6%）；在 GPQA 扩展集上总体 **57.9%**，超过各学科人类专家组（物理学家 39.9 / 化学家 48.9 / 生物学家 37.2）。
  - 五个复杂推理任务平均：Search-o1 超 RAgent 4.7%、超直接 QwQ 3.1%。
  - 多跳开放域 QA 上，agentic RAG 比标准 RAG 平均 EM 提升 **23.2%**；单跳任务无显著差异（47.8 vs 47.6）——佐证"按需多次检索"在真正需要组合知识时才有价值。
  - **top-k 缩放**：检索**1 篇**文档就超过用 10 篇文档的直接推理和标准 RAG，说明精炼模块把检索质量放大了。
  - 普通指令模型（Qwen2.5-32B）+ agentic RAG 在 GPQA 上不提升、在数学/代码上反而下降——**普通 LLM 并不会把搜索当工具用**，这是推理模型专有的能力。

- **与课程主题的关系**：Search-o1 把"搜索"从程序空间推广到**知识空间**，并把本讲两套系统的骨架统一起来——AlphaCode 在推理时探索程序候选空间，Search-o1 在推理时探索外部知识；都是"**生成 → 判断是否需要更多 → 获取外部信息 → 继续**"。Reasoning-actor 与 retrieval-critic 的分工（决定何时搜 vs 精炼怎么用）正是第 4 节"深度研究工作流"里 Agent 的核心原语，也是"自改进"的形态之一：模型不再被训练时的知识上限卡死，推理时可动态补足知识。

- **可演示的代码点**：
  - 从零实现 Search-o1 式**检索注入循环**：用 `llm_client`（脚本化 模式给脚本化轨迹）生成带 `<|begin_search_query|>` 的推理链，解析查询 → 查一个小型知识库（dict/DataFrame）→ 精炼注入 → 继续生成，统计检索轮数。
  - **不确定词检测**：统计推理链里 "perhaps / wait / likely" 出现次数，作为"知识缺口"的量化信号，画柱状图复现图 1。
  - 对比 **Standard RAG（问题级一次检索）vs agentic RAG（多轮按需）** 在一个需要多步查证的问题上的差异。

## 教学主线（想象 Stanford 老师会怎么教）

1. **动机：单个答案为什么不够。** 从一道竞赛题（如 Backspace，Codeforces rating 1500）开场：直接让 LLM 生成一段程序并提交，常常错在"题面要转成算法推理"而非 API 调用。由此引入第一条主线：程序合成 = 在巨大结构化程序空间里搜索，奖励稀疏，正确解不是唯一的。老师的类比：在干草堆里找几根对的针，且你看不到整根针（隐藏测试），只能先靠可见的样例测试筛选。

2. **三件套：采样 → 过滤 → 聚类。** 依次讲为什么每个环节都必要：
   - **采样**：一次生成不够，要高温度、随机化 prompt 元数据、Python/C++ 各半，生成百万量级；展示 `10@k` 随样本数近似 log-linear 上升（图 6）。
   - **过滤**：用样例测试当验证器，砍掉约 99% 的候选；强调这是"无监督下廉价的正确性信号"。
   - **聚类**：过滤后仍有几千候选但只有 10 次提交；用行为签名（在生成测试输入上的输出）聚类，正确解聚成大簇。手算一个 3 程序 × 3 测试输入的签名矩阵，让读者看到"输出相同=行为相同=簇"。卡点预警：读者常混淆 `pass@k`（全提交，上界）和 `10@k`（只能挑 10 个），也常忘记过滤只能靠样例测试、不能用隐藏测试。

3. **AlphaCode → AlphaCode 2：加一个重排序器，换更强的基座。** 展示同一套系统如何演进：过滤后平均剩 5 万个候选，用专门的 scoring model 在每个簇内挑最优；而换更强的 Gemini Pro 让 100 个样本就顶得上 AlphaCode 100 万个（图 3）。老师强调的权衡：**模型质量与搜索量可以互相兑换**——模型越强，需要的搜索越少，成本越低。

4. **从竞赛代码到深度研究：Search-o1。** 把"搜索"抽象成更通用的原语。先给失败案例：长推理模型会输出大量不确定词（perhaps 平均 30 次），标准 RAG（只查一次）没用，因为推理每一步需要的知识都不同。然后引出 Search-o1 的两个角色：**reasoning-actor**（模型自己决定何时生成搜索查询，`<|begin_search_query|>` 触发检索）和 **retrieval-critic**（Reason-in-Documents 先把长文档精炼成一段再注入，保持推理连贯）。与 AlphaCode 对照：一个搜程序空间，一个搜知识空间，骨架都是"生成 → 判断 → 获取 → 继续"。

5. **深度研究工作流。** 最后把三篇拼起来：deep research agent = 把复杂问题分解为子问题（规划）、对每个子问题搜索（agentic RAG）、再综合成报告。AlphaCode 的"过滤+聚类"和 Search-o1 的"reasoning-actor + retrieval-critic"就是这套工作流的可复用积木。卡点预警：读者容易认为"检索一次就够"（Standard RAG 思维），或把"精炼文档"和"直接塞长文本"混为一谈——精炼的价值在于保住推理链的连贯性。

1. **从零实现采样-过滤-聚类的代码生成管线**：用 `llm_client`（脚本化 模式提供确定性候选，或真实模型）对一个小问题生成 N 个候选程序，在样例测试上执行过滤，再用随机输入生成行为签名并聚类，最终挑 10 个提交。关键代码思路：`exec`/`subprocess` 跑 Python 代码拿输出，`collections.defaultdict(list)` 按签名分组。期望输出：过滤通过率、簇数量与大小、`10@k` 与 `pass@k` 对比。

2. **求解率随采样数量的 log-linear 曲线**：把采样预算取 10 / 100 / 1k / 10k / 100k 画 `10@k` 曲线，`x` 轴取 log 后近似直线；再用不同"质量"的模拟生成器画曲线族，观察高质量模型向左平移。期望输出：两条 log-linear 拟合直线与斜率。

3. **行为聚类小实验**：对同一道题生成若干正确/错误解，在 K 个随机测试输入上执行，输出向量即签名；正确解签名几乎相同（聚成大簇），错误解散落。用 `torch.manual_seed(42)` 保证可复现。期望输出：簇 ID 分布，正确解簇占比显著。

4. **Search-o1 式检索注入循环**：用 `llm_client` 生成含 `<|begin_search_query|>...<|end_search_query|>` 的 脚本化 推理链，解析查询 → 查一个 20 条目的知识 dict → 用第二条 prompt（Reason-in-Documents）把命中文档精炼成一句话 → 以 `<|begin_search_result|>` 形式注入继续生成。期望输出：检索轮数、注入的精炼文本、最终答案。

5. **不确定词检测**：统计推理输出中 "perhaps / wait / likely / not sure" 的出现频率，用柱状图复现论文图 1；可接在演示 4 前面做"知识缺口信号"的可视化。期望输出：每词平均出现次数柱状图。

## 作业点子（3 个）

1. **实现样例测试过滤**：考察"验证器"逻辑。给一个候选代码列表 + 样例输入/输出对，写 `filter_by_example_tests(candidates, tests)` 返回通过样例测试的代码；补全后用 assert 检查：通过率在预期区间内、且被过滤掉的代码确实输出不匹配。小提示：先用 `exec` 跑每个候选拿输出，再逐条比对样例。

2. **实现行为签名聚类**：考察"行为等价"概念。给一个"程序 × 测试输入"的输出矩阵（形状 `(num_programs, num_inputs)`，字符串或数字），写 `cluster_by_signature(outputs)` 把输出向量相同的程序归为一簇，按簇大小降序返回；补全后用 assert 检查正确解所在簇最大、簇数量符合预期。小提示：输出元组可以直接当 dict 的 key。

3. **实现 Search-o1 的检索触发状态机**：考察 agentic 循环。给定一条含 `<|begin_search_query|>...<|end_search_query|>` 的推理链文本，写 `extract_queries(text)` 返回按序出现的查询列表；再写 `inject_results(chain, query, result)` 把精炼结果以 `<|begin_search_result|>...<|end_search_result|>` 插回链中。补全后用 assert 检查：查询数与特殊符号对数一致、注入后结果包裹符号完整。小提示：用 `str.split` 按特殊符号切分，注意按出现顺序。
