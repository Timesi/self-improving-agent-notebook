## Lecture theme

The core problem this lecture solves: **how to put an agent on real software-engineering tasks, and measure its value**. Previous lectures already made the agent loop, verifiers, and tool use clear, but those were mostly on "synthetic tasks" (math, search, QA). Software engineering is the real scene where agents have the most economic value: codebases are huge (a SWE-bench repo is millions of tokens), feedback sources are rich (compile errors, test failures, profiler), success criteria are multi-dimensional (must be correct and fast). This lecture answers three nested questions: first, how test-time compute scales on code tasks (CodeMonkeys gives a complete recipe of "serial repair loop + parallel sampling + selection"); second, how to design the evaluation standard — what to do when "right" is not enough and we also need "fast" (KernelBench introduces the fast_p metric); third, what kind of "interface" between agent and underlying system is needed for alignment (Agent-System Interface).

Why it sits here: L10 is the first lecture of Part 3 (Agent Engineering). L1–L9 built the underlying abilities "loop + verification + tools + search + post-training"; this lecture assembles them into a complete system that can resolve real GitHub issues, and shows how "tasks designed for evaluation" in turn pull system design. L11 (memory) and L14 (evaluation and long-horizon tasks) follow, filling in memory systems and more systematic evaluation methods.

Pedagogically the lecture uses a "cut the engineering problem into three segments" main line: **find context → generate candidates → select an answer** (context → generation → selection). This three-segment cut (explicitly proposed by CodeMonkeys) is the general scaffold of SWE-agent system design, and runs through SWE-Agent, Agentless, and all mainstream methods.

## Close reading

### Paper 1: CodeMonkeys: Scaling Test-Time Compute for Software Engineering (arXiv:2501.14723, codemonkeys.pdf)
- **Core idea**: take test-time compute scaling (L2's theme) truly onto SWE-bench Verified, and answer "if a system is designed from the start to eat test-time compute, how should it be built". The answer is to split resolving an issue into three subtasks: find relevant files (context), generate candidate edits (generation), pick the right one from candidates (selection), then scale each: **serial scaling** = let the model and test scripts iterate repair together (each extra iteration is one more serial compute); **parallel scaling** = independently sample many repair trajectories per issue. Key insight: because many trajectories are sampled in parallel, context-finding cost can be amortized across downstream samples, so we can use the most basic method — let a cheap model (Qwen2.5-Coder-32B, run locally) read every file in the repo to judge relevance. CodeMonkeys reaches 57.4% on SWE-bench Verified, costing about $2300.
- **Key formulas / algorithms**:
  - Three-segment evaluation metrics: Context uses recall (fraction of problems where all files that need editing are placed in context, 92.6% under a 128k cap); Generation uses coverage (fraction of problems with at least one sampled edit correct, best 69.8%); Selection uses final score (fraction of problems whose submitted edit is judged correct by official tests, 57.4%). The relation: coverage is the "generation ceiling" (upper bound of oracle selection); selection decides how much of that ceiling we recover.
  - Context pipeline: Qwen2.5-Coder scans file by file for relevance (Python files only, exclude test directories, average 2.94M tokens/problem) → summarize relevant files → Claude ranks (temperature 0, repeat 3 times, take average rank) → pack into a context window of at most 128k tokens. Average context 74,570 tokens, 50.5× compression vs full; scan+rank together are only 15% of cost (because amortized over 10 downstream trajectories).
  - Generation stage = two back-to-back **state machines** (state-machine abstraction from Moatless Tools): ① Testing State Machine independently iterates a test script that can reproduce the issue (standalone Python, exit 0 means repaired, exit 2 means not); ② Editing State Machine uses that test as seed, iterates edits in aider-style diffs, and is allowed to change tests at the same time — the paper's emphasized "two-sided debugging": tests must fail on the unedited repo and pass after the edit. Each iteration feeds execution output back to the model. 10 state-machine pairs per issue, at most 8 iterations each, temperature 0.5.
  - Selection stage (4 methods compared): ① test majority vote (run each of 10 generated tests on each of 10 edits, pick the one that passes most); ② pure model selection; ③ model selection but first filter to top-3 by tests passed; ④ **selection state machine** + top-3 filter: let the model write new tests that "can distinguish candidates", run them then decide whom to pick or write more tests, at most 10 iterations. Best is ④, 57.4%.
  - Key numbers: random selection only 45.8%, oracle (=coverage) 69.8% — selection recovered about half the gap between random and oracle. Barrel of Monkeys (merge CodeMonkeys edits and SWE-bench Verified leaderboard top-4 submissions into a 5-sample pool, coverage 80.8%) with the selection state machine reaches 66.2%, above the best single method in the pool (Blackbox 62.8%), only 5.5pt below o3's reported 71.7%.
  - Cost breakdown (table 1): total $2291.90. Generating edits 59.6%, generating tests 19.2%, relevance scan 14.6%, selection 5.8%, ranking 0.9%.
  - Scaling law (figure 5): coverage grows with "number of state machines × iterations per machine", largest gain in the first few iterations; **under the same total budget, different serial/parallel allocations often get similar coverage** — but they are not fully interchangeable: sampling more in parallel makes selection harder; deep serial trajectories skip the selection problem, except when the model "wrongly approves" its own edit, raising the iteration cap cannot recover, while adding a new parallel trajectory can always "start over".
  - Appendix: replace Claude with DeepSeek-V3 for generation/selection, on a 100-problem subset reaches 86.8% of Claude's score, but the API is an order of magnitude cheaper — "cheap model, many samples + strong selector" is the cost-sensitive choice.
- **Key experimental results**: 57.4% (SWE-bench Verified, about $2300/500 problems); coverage 69.8%; with oracle selection 69.8% beat every then-leaderboard submission except o3. The selection stage shows "whether we pick right" is crucial to the final score: random 45.8% → simple vote 53.0% → model selection 52.0% → top-3+model 55.6% → **top-3+selection state machine 57.4%**.
- **Relation to the lecture theme**: this lecture's first brick — upgrade L2's "sample+verify" into a complete agent loop that can run on a real GitHub repo. The three-segment split (context/generation/selection) is the lecture's teaching skeleton; the hard requirement "let the model write tests" serves two things at once: finer execution feedback for iteration, and an (imperfect) verifier for selection — L3's verifier idea landing in the code domain. The state machine is the most directly implementable template of "building a SWE-Agent loop" (OUTLINE point 4).
- **Demo-ready code points**: build a mini state machine from scratch (generate edit+test → run tests → take exit-code feedback → iterate); implement the coverage formula and plot a "sample count–coverage" curve; implement three selectors (test majority vote / model selection / selection state machine) and contrast on a synthetic candidate pool; reproduce the cost accounting of "amortizing context cost".

### Paper 2: KernelBench: Can LLMs Write Efficient GPU Kernels? (arXiv:2502.10517, kernelbench.pdf)
- **Core idea**: push evaluation from "is the code correct" to "is the code correct and fast". Give the LLM a PyTorch reference implementation (`Model` class), require it to emit a `ModelNew` class with the same interface but custom CUDA/Triton kernels inside, then automatically evaluate two axes: functional correctness (compare outputs on random inputs) and performance (wall-clock speedup). 250 tasks in three levels by operator count: Level 1 single operator (100), Level 2 operator sequences (100, tests fusion), Level 3 full architectures (50, AlexNet/MiniGPT). Motivation from reality: key kernels such as FlashAttention appeared 5 years after Transformers, and another 2 years after a hardware change — if an LLM can automatically write efficient kernels, the value is realized directly as lower inference/training cost and energy.
- **Key formulas / algorithms**:
  - fast_p metric: $\text{fast}_p = \frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[\text{correct}_i \land \text{speedup}_i > p]$, where $\text{speedup}_i = T_{\text{Model}}/T_{\text{ModelNew}}$. p is a speedup threshold: fast_0 is pure correctness, fast_1 is "correct and faster than PyTorch Eager". Treating p as a knob lets us plot a whole "speedup distribution" curve, and later upgrade the baseline (e.g. vs torch.compile). Evaluation details: correctness uses 5 groups of random inputs; performance 3 warmups, 100 timings take the mean (CV<3%); only one kernel on the GPU at a time.
  - Task format: input is a PyTorch `Model` containing `get_inputs()`/`get_init_inputs()`; output `ModelNew` uses `torch.utils.cpp_extension.load_inline` for inline CUDA (the paper gives full add/matmul examples). The LM itself decides which operators to optimize and with what techniques (fusion, tiling, shared memory, tensor core/wmma, PTX).
  - One-shot baseline: a single in-context example (add operator) + greedy decoding. All frontier models average faster than PyTorch Eager on <20% of tasks (table 1): DeepSeek-R1 L2 36%, L1 12%; o1 L2 24%, L1 10%; the rest mostly single digits; even lower vs the torch.compile baseline.
  - Two test-time methods (same 10-call budget, table 2): **repeated sampling** (high-temperature parallel sample k, fast_p@k = at least one meets the bar) and **iterative refinement** (multi-round feed generation G + execution feedback E + profiler feedback P back to the model). Iteration is better (5 of 6 cases), and feedback combination G+E+P is strongest: DeepSeek-R1 on Level 2 from one-shot 36% to 72% (figure 6), L1 12%→43%, L3 2%→18%. Pure correctness (fast_0, table 9) after E, R1 exceeds 90% on L1/L2. Repeated-sampling example: DeepSeek-V3 L2 from 4% (one-shot) to 37% (k=100), but if the model's inherent probability on a class of tasks (34 convolution variants) is too low, more samples cannot recover.
  - Failure-mode attribution (figure 2): execution failure (compile/OOB/runtime error) vs functionally incorrect (shape/value wrong). Reasoning models (o1, R1) have clearly fewer execution failures (total errors <55% vs others >70%), but **all models struggle equally on functional correctness**. The authors attribute this to CUDA being a low-resource language — only 0.073% of The Stack v1.2.
  - Interesting kernels (section 6): 13× diag-matmul (Claude, change diagonal matrix multiply to per-row scale, pure algorithmic optimization); 2.9× GELU fusion (DeepSeek-V3, including constant folding); 2.8× cosine similarity (o1, shared-memory reduction); 2.6× matmul+divide+sum+scale fusion (Sonnet). But never a usable tensor-core instruction.
  - Cross-hardware (table 14 / figures 8–9): one-shot kernels do not generalize across hardware, R1 L2 fast1 is L40S 36% vs A10G 47%. Providing hardware specs (TFLOPS/bandwidth) in context helps little; few-shot demonstrations (fusion/tiling/FlashAttention) actually lower overall fast1 (the model is more aggressive → more execution failures), but on the correct subset o1 applied tiling to 77% of GEMMs.
  - Evaluation system (appendix H): three-stage pipeline (parallel generation → CPU nvcc precompile cache → GPU single-kernel one-by-one timing); iteration experiments use "GPU orchestrator + finite state machine + semaphore grabbing the GPU", plus a UI to visualize trajectories.
- **Key experimental results**: even the strongest reasoning model under one-shot only matches the PyTorch baseline on <20%; iterative feedback (E+P) pulls R1's L2 fast1 from 36% to 72%; both repeated sampling and iteration beat one-shot, but the ceiling is set by the base model. The benchmark's property "raise p and it gets harder" lets it keep evolving as models improve.
- **Relation to the lecture theme**: this lecture's second brick — showing how "designing an environment for evaluation" drives agent-system design. KernelBench's loop (generate→compile→execute→profiler feedback→generate again) is a special case of the SWE-agent loop under the goal "performance optimization"; fast_p shows how to compress "multi-objective (correct+fast)" into one scalar metric. It also points out that an agent's real bottleneck is often not "thinking correctly" but "data scarcity" (CUDA corpus 0.073%).
- **Demo-ready code points**: implement fast_p in numpy and plot the correct+speedup curve as p rises from 0; a CPU "pseudo kernel evaluation" (time and correctness of per-operator vs fused implementations, feeling fusion gain); a simulated "generate→compile-error feedback→generate again" iteration loop, watch fast1@N rise with rounds; simulate a repeated-sampling coverage curve.

### Paper 3: On the Need to Align Intent and Implementation in Uncertainty Quantification (arXiv:2506.03037, agent-system-interfaces.pdf)
- **⚠️ File issue**: the actual content of `papers/lecture-10/agent-system-interfaces.pdf` is not this lecture's expected "Improving Parallel Program Performance with LLM Optimizers via Agent-System Interfaces". The paper that truly corresponds to agent–system interface design should be arXiv **2410.15625** (Wei, Nie, Teixeira, Yadav, Lee, Wang, Aiken, ICML 2025, Stanford). This PDF holds another position paper: Trivedi & Nord (Fermilab/University of Chicago) *On the Need to Align Intent and Implementation in Uncertainty Quantification for Machine Learning*. **When writing the notebook, if covering the "Agent-System interface design" section, re-download 2410.15625**; the notes below on the actual file are still worth keeping, because they give a transferable analysis of "aligning intent and implementation".
- **Core idea**: a position paper arguing that "quantified uncertainty must be anchored to its inference goal". The core pathology is called **construct drift**: uncertainty is computed for A, then used to support a conclusion about B (e.g. treating "variance of model outputs" as "what the model does not know"). The authors give a diagnostic frame: first classify the "estimation target" (what is being estimated), then classify the "uncertainty construct" (what logic expresses uncertainty), then require the two to align via an "epistemic contract", and test with three "credibility axes".
- **Key formulas / algorithms**:
  - Estimation-target taxonomy (six kinds): estimation (pure numerical summary, no commitment), prediction (predict a future observable), inference (recover latent parameter θ), predictive inference (model-free coverage guarantees on future observations, e.g. conformal), indirect inference (auxiliary statistics when there is no likelihood), simulation-based inference (SBI, replace likelihood with a simulator, NPE/NLE/NRE).
  - Uncertainty-construct families (four, each a probability interpretation): frequentist (long-run repeated guarantees, e.g. confidence intervals, conformal sets), Bayesian (coherent belief update, credible regions), fiducial/hybrid (Fisher, derive a distribution from the data-generating mechanism), logical probability (Keynes/Carnap, degree of entailment from evidence to hypothesis).
  - Epistemic contract (table 2): target → warrant → construct. Example: prediction → long-run coverage → conformal set; parameter inference → belief coherence → credible region; SBI parameters → learned approximation → NPE posterior.
  - Three credibility axes (section 5): ① formal guarantees (is there a theory: coverage theorems, posterior consistency); ② empirical reliability (does it hold in practice: SBC, posterior predictive checks, calibration curves); ③ model correspondence (does it respect domain structure: symmetries, conservation laws, causality). The three axes are not interchangeable — a method may have valid coverage and look good on a benchmark while completely ignoring physical structure.
  - SBI checklist (land the three axes on simulation inference): theory check (what the method claims to guarantee), forward checks (can posterior samples through the simulator reproduce the observed-data distribution), inverse checks (can known parameters be recovered from simulated data, testing identifiability and calibration), degeneracy mapping (whether parameter space has observationally equivalent directions), global structure comprehension (full check of the joint p(θ,x)).
  - Typical misalignment cases (section 6, each violating which axis): treating deep-ensemble cross-model variance as "epistemic uncertainty" (no calibration guarantee, violates axes 1&2); conformal intervals only guarantee marginal coverage but lack domain ontology (violates axes 2&3); NRE trained on a fast proxy simulator yields overconfident posteriors and poor coverage (Delaunoy et al., violates axes 1&3); reporting both a frequentist p-value and a Bayesian credible region on the same detection creates a false "contradiction" (warrant confusion); conformal fails on subgroups (calibrated coverage but not calibrated explanatory power).
  - Recommendations (section 7): explicitly declare the inference chain (target/loss/construct/warrant), pick constructs by use, do both forward and inverse checks, do not mix constructs (prediction interval ≠ credible region), use simulators as test instruments, go beyond i.i.d. evaluation, study model stability, clarify terms across disciplines.
- **Key experimental results**: this is a position paper, no experimental curves; the most valuable outputs are a diagnostic checklist (table 3's cross-cutting diagnostics: marginal coverage, conditional coverage, sharpness, OOD behavior, aleatoric/epistemic separation, composability, decision alignment, etc.) and the operable discipline "declare the inference chain before making claims".
- **Relation to the lecture theme**: this is the lecture's third brick's **conceptual base**. Although it is about statistical uncertainty, the skeleton transfers fully to agent–system interface design: the agent's "intent" (what it wants to do, what it claims) must align with the system's "implementation semantics" (how it actually executes, what numbers it reports), otherwise we get an engineering version of construct drift — e.g. the agent treating test pass rate as "repair success", coverage as "accuracy". 2410.15625 lands the same sentence "align intent and implementation" at the system layer: give the LLM optimizer a DSL (make mapping decisions explicit as a searchable space) plus an AutoGuide (translate raw execution output into actionable natural-language feedback), rather than letting the model face a bare C++ system. This also echoes L14 (agent evaluation): the evaluation metric itself is an "interface"; if the metric is defined wrong, a good system is wasted.
- **Demo-ready code points**: with synthetic data demo "variance is not uncertainty" (cross-model variance has no coverage guarantee); write a mini conformal-style calibration check contrasting raw std vs calibrated interval coverage; turn "declare the inference chain" into a template function so students declare target and metric for their own scripted evaluation.

> Note: quick points of the paper that truly matches this lecture's OUTLINE section 3 "Agent-System interface design" (arXiv:2410.15625, correct file missing), for after re-download: the frame is named **Agent-System Interface (ASI)**, two parts DSL + AutoGuide. The DSL turns writing "mappers" of tasks-to-processors / data-to-storage from C++ into declarative, shrinking code volume about 14× on average, and explicitly defines a structured searchable space; AutoGuide translates raw execution output (e.g. "assertion failed: stride mismatch") into actionable advice ("memory layout is wrong, adjust layout constraints"). Result: a generative optimizer with 10 iterations already beats OpenTuner run for 1000 iterations (3.8× faster; 11× faster at the same 10 iterations); on 9 benchmarks (Circuit/Stencil/Pennant + 6 matmul algorithms) up to 1.34× speedup vs expert mappers; tuning time from days to about 10 minutes; ablation: DSL single-generation success rate 80% (C++ 0%), full feedback (execution+explanation+advice) substantially beats any degraded feedback.

## Teaching thread (how a Stanford instructor might teach this)

Organized as "real task → split → evaluation → interface"; the three papers are four steps of the same SWE story:

1. **Set the target first: SWE-bench meets test-time compute**. Recap L2's conclusion — LLM Monkeys found coverage grows log-linear with sample count, but "can sample a correct solution" ≠ "can submit a correct solution". A striking number: CodeMonkeys random selection is only 45.8%, oracle selection (i.e. coverage) 69.8% — the correct solution was generated but not selected. This is the SWE version of the "generation–verification gap" (echoing L3). Here we give the lecture scaffold: cut repairing an issue into **find context → generate candidates → select an answer**.
2. **CodeMonkeys: how to truly eat test-time compute into the system**. Segment by segment: ① context (because we sample 10 trajectories, per-file scan cost is amortized, so the naive method is actually economical — the first example of "design backwards for test-time compute"); ② generation (two back-to-back state machines: first independently iterate a test, then let edit and test correct each other, stressing two-sided debugging "tests must fail on the unedited repo and pass after the edit"); ③ selection (majority vote vs model selection vs selection state machine, approaching oracle step by step). **Where readers stall**: what is the difference between serial scaling (more iterations) and parallel scaling (more trajectories) — use figure 5's "frontier curve": coverage is similar at the same budget, but parallel makes selection harder, serial hits the ceiling of "the model wrongly approves".
3. **KernelBench: test "right" and "fast" at the same time**. The instructor asks: CodeMonkeys evaluation is binary (repaired / not), but if the task goal is "performance"? Introduce fast_p: one scalar encodes both correctness and speedup, p is a knob. First the striking one-shot result (frontier models <20% faster than PyTorch), then the solution: iterative execution feedback E + profiler feedback P takes R1's L2 from 36%→72%. **Where readers stall**: why adding execution feedback (E) alone is significant, while adding profiler (P) helps only some models — because "correctness feedback is less informative than a compile error", and whether the model can digest profiler output depends on the base. Can show a real wmma kernel (figure 10) of "the model tries hardware instructions it has not digested".
4. **Agent-System interface: intent must align with implementation**. Borrow a concept from the UQ paper: construct drift = uncertainty computed for A used to support a conclusion about B. Translate to the system layer: the agent's intent (claims it repaired, claims it got faster) must align with the system's implementation semantics (how tests judge, how timing is timed), otherwise metrics drift. The real ASI paper (2410.15625) gives a landing: use a DSL to make "mapping decisions" explicit as a searchable space, use AutoGuide to translate raw execution output into actionable advice — the interface is a "translation contract" between agent and system.
5. **Close and preview**: one axis strings the lecture — a real-task agent system = context retrieval + repair loop + selector + a goal-facing evaluation interface; preview L11 (memory: Cartridges/MemGPT solve context management), L14 (evaluation: SWE-bench series and long-horizon evaluation).

## Code demo ideas (3–6)

1. **Mini SWE repair loop (serial test-time compute)**: implement a simplest state machine from scratch — loop body is "LLM generates edit + test script → run tests on a scripted repo → take exit code/output as feedback → generate again", until the model approves or an iteration cap. Use `llm_client.py`'s scripted branch to provide scripted "edits getting better", track tests passing each round. Expected output: a curve visualizing "iteration count × repair quality", showing serial-scaling diminishing returns (largest gain in the first few iterations, matching paper figure 5).
2. **Parallel-sampling coverage curve**: given per-problem "single-sample success probability" (synthetic data, varied difficulty), implement coverage = 1 − ∏(1 − p_i), plot a log-linear "sample count N vs coverage" curve; then a serial+parallel budget-allocation version (split total budget B into B_serial rounds × B_parallel trajectories), verify "same budget, different allocation, similar coverage". Expected output: reproduce the intuition of LLM Monkeys / CodeMonkeys figure 5.
3. **Three-selector contrast (test vote / model selection / selection state machine)**: synthesize a batch of candidate edits (each with a hidden correctness label + pass/fail of a batch of generated tests), implement "test majority vote", "direct model selection", "filter top-3 then select", compare each's score vs oracle (coverage). Expected output: selection state machine + filter > pure vote > random, quantifying "how much of the random–oracle gap selection recovered".
4. **fast_p and speedup distribution**: with numpy make a batch of "candidate kernels" (each with `is_correct` and `speedup`), implement the fast_p formula and plot the falling curve as p goes from 0 to 2; then a simplified "correctness check" (random-input output tolerance) showing how 5 groups of random inputs approximately judge correctness. Expected output: fast_0 = pure correctness, fast_1 = meet-the-bar rate, higher p harder, showing "the threshold is a knob".
5. **CPU fusion demo (pseudo KernelBench)**: pick a simple operator sequence (e.g. `matmul → ReLU → sum(dim=1)`), implement with numpy per-operator vs hand-fused, time and assert numerical agreement. Expected output: fused version's speedup magnitude, so students can feel KernelBench Level 2's "fusion" motivation without a GPU. **Experiment corpus**: fixed seed, fixed shape, multiple timings take the median.
6. **Intent–implementation alignment: variance is not uncertainty**: synthesize a simple regression task, train (or simulate) several models, contrast two "uncertainties": ① cross-model output variance (common deep-ensemble practice); ② a calibrated interval with a marginal coverage guarantee. On a hold-out set compute how little variance explains real error, while the calibrated interval has approximately nominal coverage. Expected output: a "coverage vs nominal level" calibration curve, demonstrating construct drift (echoing the UQ paper's three credibility axes).

## Exercise ideas (3)

1. **Coverage and sample count**: given per-problem single-sample success probability `p` and sample count `n`, fill in the coverage formula. `assert abs(coverage(0.2, 10) - (1 - 0.8**10)) < 1e-9`, `assert coverage(0.2, 100) > coverage(0.2, 10)`. Hint: coverage = probability at least one succeeds = 1 − probability all fail; problems assumed independent.
2. **fast_p computation**: given a candidate list (each item `(is_correct, speedup)`), fill in `fast_p(candidates, p)`. `assert fast_p(cands, 0) == correct_count/total`, `assert fast_p(cands, 1) <= fast_p(cands, 0.5)`. Hint: combine the two conditions "correct" and "speedup > p" with and, then take the mean.
3. **Selector that majority-votes with tests**: given a `passes` boolean matrix (rows=generated tests, columns=candidate edits), fill in "pick the edit that passes the most tests, on a tie pick the shortest diff". `assert select(passes, lengths) == expected_index`. Hint: `passes.sum(axis=0)` is per-column pass counts; on a tie, among the max-pass group take min `lengths`.
